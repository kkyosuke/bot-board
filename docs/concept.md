# bot-board 企画・要件書

作成日：2026-11-18 ／ 状態：初稿・設計提案

## 1. コンセプト

**Botが仕事を進め、人はスワイプで方向を決める。**

ChatGPT、Muse、Grok、Claudeが共通のタスクを読み書きできるアプリ。Botがタスクの作成・分解・整理・進捗更新を担当し、人には判断が必要な内容だけを1枚ずつ提示する。人はTinderのようにカードをスワイプして選択する。

カンバンは裏側の状態管理に使う。日常の主画面は判断カードで、タスクの一覧編集や列間のドラッグ操作を人に求めない。

## 2. 確定した要望と提案の区別

| 区分 | 内容 |
| --- | --- |
| ユーザー要望 | タスク管理のカンバンアプリ |
| ユーザー要望 | 基本はスマートフォン（SP）、PCでも利用できる |
| ユーザー要望 | ChatGPT / Muse / Grok / Claudeが操作しやすい |
| ユーザー要望 | 人は基本的に管理操作をせず、表示されたカードをスワイプして選ぶ |
| 本書の提案 | 右＝採用、左＝見送り。保留は明示的な「あとで」で扱う |
| 本書の提案 | 最初は個人利用・1ワークスペース。承認者は1人 |
| 本書の提案 | 外部Bot用の共通APIとMCP、継続稼働するBot用の実行ワーカーを分ける |
| 未確定 | Museの正式名称・URL、各Botを公式チャットから使うかAPIで動かすか |

以下の画面・状態・数値は実装に向けた提案であり、ユーザーが全項目を確定したものではない。

## 3. 基本体験

1. 初回だけ目的・接続先・Botに任せる範囲を設定する。目的は外部Botとの会話から登録できる形も用意する。
2. Botが目的に沿ってタスクを作り、必要な調査・下書き・整理を進める。
3. 方針選択や成果の確認など、人の判断が必要になったらカードを提出する。
4. 人がカードを読み、右へスワイプして採用するか、左へスワイプして見送る。
5. Botが結果を受け取り、作業を進める、別案を作る、または停止する。
6. 完了結果は履歴に残る。判断が不要な進捗更新をスワイプ対象に混ぜない。

継続して自動で動くには、判断結果を受け取って動作する実行ワーカーが必要。公式チャットに接続しただけでBotが常時動くとは扱わない。詳細は[Bot連携・状態設計](bot-integration.md)を参照。

### 利用例

「新しいアプリの企画を進めたい」という目的から、Botが調査タスクと企画案を作る。人には「初版はスマホの判断カードに機能を絞る？」というカードが届く。採用すると、その方針がタスクに記録され、Botが次の設計へ進む。見送った場合は採用済みにせず、Botへ別案の検討を返す。

## 4. 判断カード

1枚で1つの判断を扱い、読まなくてもよい内部ログや長い会話は表示しない。

| 要素 | 内容 |
| --- | --- |
| 見出し | 「何を選ぶのか」を短い疑問文で示す |
| 要約 | 提案と理由を2〜4行で示す |
| 結果 | 採用・見送りでそれぞれ何が起きるか |
| 判断材料 | 費用、期限、影響先など、この判断に必要な情報だけ |
| 出典・成果 | 下書きや調査結果のプレビュー／詳細への導線 |
| 提案元 | Bot名、関連タスク、提出日時 |
| 操作表示 | 左「見送る」、右「採用する」を常時表示 |

カードの種類は「方針の採用」「候補の選択」「成果の受け入れ」とする。対象の文面・成果物・操作内容を固定し、その版に対して判断を保存する。

### スワイプの意味

- 右：表示された提案を採用する。タスク完了や外部公開を常に意味するわけではなく、カードに示された結果だけを許可する。
- 左：その提案を採用しない。タスクや成果物自体は削除しない。Botには見送りとして返す。
- あとで：未決定のまま後ろへ回す補助操作。MVPでは時刻指定を不要にする。
- スワイプ途中：移動量が閾値未満ならカードを元へ戻す。上下スクロールは判断として扱わない。

左右の基本的な意味は全カードで統一する。「左で削除」「右で別の提案を拒否」のような逆転を避ける。色に加えて文字・アイコンを使う。

### 複数案からの選択

同じ選択グループの候補を順に表示する。必要なら詳細で他候補と比較できる。1件を採用すると同じグループの残りは選択対象から外す。全候補を見送った場合は「選択なし」とし、Botに再提案を返す。最後の候補を自動採用しない。

### 誤操作・通信失敗

採用／見送り後は次のカードを表示し、5秒間「取り消す」を出す提案とする。この間は判断を仮確定として扱い、Botには実行可能な判断として渡さない。サーバーが猶予の終了と取り消しを排他的に処理する。

確定後に作業が始まった場合は、取り消しで実行を巻き戻したように見せない。変更希望は新しい判断として扱う。MVPでは外部公開・送信・課金などの実行を対象に含めない。

オフライン時は未送信と表示し、判断を確定しない。復帰後はカードの最新版を確認してから再操作する。保存が失敗したカードは判断待ちに戻す。

## 5. 画面構成

| 画面 | 役割 | 日常の使用 |
| --- | --- | --- |
| 判断 | カードを1枚ずつ表示。件数、スワイプ、あとで、取り消し | 主画面 |
| 状況 | Botごとの進行状況、待機理由、タスクの読み取り専用カンバン | 必要なときだけ |
| 履歴 | 採用・見送りと成果を確認 | 必要なときだけ |
| 接続・設定 | Bot接続、目的、権限、停止・再開 | 初回と例外時 |

カード詳細は判断画面から開く。日常利用にタスクの手入力、担当変更、列移動、コメント記入を必須にしない。設定・復旧・任意の詳細閲覧はスワイプ以外の操作を認める。

### SP

- 幅360〜430pxを主な設計基準にし、320pxでも内容を欠落させない。
- カード1枚を中央に置き、主要操作を親指で届く下部に配置する。
- 長い説明はカード内の短い要約と詳細に分け、縦スクロールと横スワイプを区別する。
- 端末の戻るジェスチャーに配慮し、画面端からの操作を独自スワイプで奪わない。
- 読み込み中、判断0件、Bot実行中、Bot未接続、失敗をそれぞれ表示する。

### PC・アクセシビリティ

- PCでもカードを主役にし、余白に進捗や詳細を表示する。
- マウスドラッグと「見送る／採用する」ボタンで同じ判断を行える。
- キーボード・スクリーンリーダーでは名前付きボタンを利用できる。スワイプを必須にしない。
- 操作領域は44×44 CSS px以上を設計目標とし、動きを減らす設定に対応する。

## 6. Botに任せる範囲

| Botが行う | 人が判断する |
| --- | --- |
| タスクの作成・分解・分類 | 進める方針・優先する案 |
| 担当の取得・進捗更新 | Botが解消できないトレードオフ |
| 調査・下書き・成果リンクの登録 | 確認が必要な成果の受け入れ |
| 判断カードの作成・不要カードの取り下げ | 接続・権限設定と例外対応 |

細かな進捗のたびに承認を求めない。事前に許可した範囲ではBotが進め、範囲外や不明点だけカードにする。Botは自分の判断カードを人の代わりに承認できない。

## 7. MVPと段階

### MVPに含める

1. 個人用の目的・タスク・成果・判断カードの永続化。
2. SP中心のスワイプ体験、PCの代替操作、履歴と状況表示。
3. 右／左／保留、取り消し猶予、候補の排他選択。
4. Bot共通の読み書きAPIとMCP、操作元・変更履歴・権限制御。
5. 少なくとも1つの継続稼働するBot経路で、提案→人の判断→自動再開を検証する。
6. 複数Botの重複作業・競合更新を防ぐ担当取得と版管理。

### 対象Botへの展開

ChatGPTとClaudeは公式チャットからの接続を検証する。GrokはAPI経由のワーカー候補として検証する。Museはサービス特定後に方法を決める。**MVPの一部経路が動いても「4種類対応済み」と表示しない。** 全対象の連携を目指し、各経路の到達点を個別に管理する。

### 後続候補

プッシュ通知、複数人の承認、複数ボード、検索・分析の強化、オフライン判断、外部サービスへの公開・送信、Bot間の高度な自動分担。ネイティブアプリ化・課金・運用基盤の選定はこの初稿では確定しない。

## 8. 受け入れ条件

| ID | 確認すること |
| --- | --- |
| UX-01 | 初回設定後、通常の1サイクルを人がタスク編集せずスワイプだけで進められる |
| UX-02 | SPとPCで同じカードを読み、同じ判断を保存できる |
| UX-03 | 採用／見送りによる結果が操作前に分かる |
| UX-04 | 縦スクロールと閾値未満のドラッグでは判断が送信されない |
| UX-05 | ボタン・キーボードでもスワイプと同じ結果になる |
| DEC-01 | 5秒以内の取り消しが成功した場合、Botがその判断で着手しない |
| DEC-02 | 二重送信・2端末の操作でも判断と後続作業が二重確定しない |
| DEC-03 | 古いカードや変更された提案を採用しようとすると、再確認用のカードになる |
| DEC-04 | 候補の採用は1件だけ。全件見送り時に勝手に採用しない |
| BOT-01 | 人の判断確定後、稼働中ワーカーが次の作業を取得して再開できる |
| BOT-02 | Botは権限のないタスクを読めず、人の判断も偽造できない |
| BOT-03 | 作業失敗時に完了と表示せず、理由と再試行状況が分かる |

これらは実装後に検証する条件。現時点では実装・接続試験を行っていない。

## 9. 次に確定する事項

- Museの正式名称・URLと、想定する利用形態。
- 最初にBotへ任せたい実例（企画、調査、開発など）。
- 公式チャットからの手動起動と、APIワーカーによる継続実行の優先順位。
- 見送った理由を入力せずとも、別案の提案で十分に回るか。
- 1日あたりのカード件数、実行費用の上限、初回設定の許容範囲。

実装順は「連携の小規模検証」→「スワイプ体験の試作」→「判断からBot再開までの縦通し」とする。
